# QA Platform Production Test — Baseline Workflow

**Version:** 2.0
**Created:** 2026-03-24
**Status:** Baseline — iterate and adjust per platform

---

## Overview

Standard workflow for production-testing a QA platform built with the Isagawa framework. Uses a master repo → test repo copy pattern. All prod tests run inside the test repo.

## Architecture

```
MASTER REPO (golden copy)
  ├── framework/          ← platform code
  ├── .claude/            ← domain spec + kernel
  ├── run-task.sh         ← shell scripts
  └── CLAUDE.md           ← kernel bootstrap
         │
         │  copy
         ▼
TEST REPO (disposable workspace)
  ├── framework/          ← same code
  ├── .claude/            ← same kernel (protocol + hooks already built)
  ├── run-task.sh         ← same scripts
  ├── tasks/prod-test/    ← test task files (copied or generated)
  ├── _test/docker/       ← Docker infra (created during test)
  └── _test/fixtures/     ← live host config (created during test)
```

## Execution Model

Two levels of `run-task.sh`:

1. **Outer run-task.sh** — runs in sr-dev-workspace, orchestrates the full workflow (master setup, copy, Docker infra)
2. **Inner run-task.sh** — runs inside the test repo, executes L1/L2/L3 test tasks under kernel enforcement

```
sr-dev-workspace/run-task.sh
  └── spawned agent per task
        ├── MASTER phase: set up master repo, run domain-setup, validate
        ├── COPY phase: copy master → test repo
        ├── INFRA phase: Docker setup in test repo
        └── TEST phase: spawned agent runs test-repo/run-task.sh
              └── inner spawned agents run L1/L2/L3 inside test repo
```

### Shell Scripts

```bash
# Outer: orchestrate from sr-dev-workspace
./run-task.sh . [max_iterations] ssh-prod-test

# Inner: test execution inside test repo (invoked by outer tasks)
./run-task.sh [test_repo_path] [max_iterations] prod-test
```

### Task Personas

| Persona | Role | Where |
|---------|------|-------|
| **Outer spawned agent** | Sets up master, copies repo, builds Docker, kicks off inner tests | sr-dev-workspace |
| **Inner spawned agent** | Executes L1/L2/L3 test tasks under kernel enforcement | test repo |
| **run-task.sh (outer)** | Orchestrates master→test→run flow | sr-dev-workspace |
| **run-task.sh (inner)** | Runs test tasks sequentially | test repo |
| **User** | Kicks off outer shell script, reviews final report | sr-dev-workspace |

## Phases

```
MASTER → VALIDATE → COPY → INFRA → TEST → REPORT → CLEANUP
```

| Phase | Purpose | Where |
|-------|---------|-------|
| MASTER | Assemble master repo: kernel + domain spec + framework + shell scripts | master repo |
| VALIDATE | Run domain-setup, verify protocol + hooks + commands | master repo |
| COPY | Copy master → fresh test repo | filesystem |
| INFRA | Write Dockerfile, SSH keys, docker-compose, start container | test repo |
| TEST | Run L1/L2/L3 via inner run-task.sh inside test repo | test repo |
| REPORT | Aggregate results into validation-report.json | test repo |
| CLEANUP | Tear down Docker container | test repo |

## Master Repo Setup

The master repo is the **golden copy** with everything pre-configured:

1. Framework code (`framework/_reference/`)
2. Kernel files (CLAUDE.md, `.claude/commands/kernel/`, `.claude/hooks/`, `.claude/state/`)
3. Domain spec (`.claude/skills/[domain-layer]/`)
4. Shell scripts (`run-task.sh`, `run-task-batch.sh`)
5. Protocol + hooks generated by `/kernel/domain-setup`

After domain-setup, the master has a working kernel. Copying it gives the test repo a ready-to-go environment — no setup needed in the test repo.

These tasks use **relative paths** — they run inside the test repo, so `framework/_reference/` resolves locally.

## L3 Test Pattern

L3 tests exercise the **framework directly** against a live target:

```python
import sys
sys.path.insert(0, "framework/_reference")

from ssh_interface import SSHInterface
from validators.[name] import [Validator]

hc = {
    "host": "localhost",
    "port": 2222,
    "username": "root",
    "key_path": "_test/docker/test_key"
}

with SSHInterface(hc) as ssh:
    validator = [Validator](ssh)
    results = validator.validate([args])
    assert [condition], "[message]"
    print("PASS: [description]")
```

Key: L3 tests use the **test automation framework** (the deliverable), not the domain spec. All paths relative to test repo.

## Docker Target Pattern

```
_test/docker/Dockerfile        → Rocky Linux 9 + openssh-server + key auth
_test/docker/docker-compose.yml → port 22 → 2222
_test/docker/test_key           → SSH key pair
_test/fixtures/live_host_config.json → host config for framework
```

## Adapting for Other Platforms

1. **Change the master repo** — different framework, different domain spec
2. **Change the Docker target** — different base image, different services
3. **Change the framework imports** — different interface/validators
4. **Change the host config** — different expected packages/services/configs
5. **Keep the phase structure** — MASTER → VALIDATE → COPY → INFRA → TEST → REPORT → CLEANUP
6. **Keep the execution model** — outer run-task.sh orchestrates, inner run-task.sh tests
