## Bootstrap Sequence

### What must exist BEFORE domain-setup can run?
1. `CLAUDE.md` — tells the agent about the kernel loop and commands
2. `.claude/commands/kernel/*` — provides the commands the agent invokes
3. `.claude/hooks/*` — provides enforcement (gate enforcer, test failure detector)
4. `.claude/settings.local.json` — registers hooks (without this, hooks are dead code)
5. `.claude/skills/kernel-domain-setup/*` — provides the domain-setup skill itself
6. `.claude/skills/autonomous-cycling/*` — provides the cycling skill

### What does domain-setup create? (reading a spec)
7. `.claude/protocols/[domain]-protocol.md` — indexed protocol
8. `.claude/lessons/lessons.md` — initial lessons index
9. `.claude/state/[domain]_workflow.json` — workflow state
10. `.claude/state/session_state.json` — session state
11. Domain-wrapped commands (if spec has commands to wrap)

### What does the domain spec provide? (Layer 2 — separate SKU)
12. `.claude/skills/[domain]-guidance/*` — the spec's skill files
13. Domain commands — the spec's workflow commands
14. Framework/reference code — if the spec includes reference implementations

## Key Insight

**domain-setup is the constant primitive** — it always exists. It reads specs and builds governance.

**The kernel spec is the first domain spec** domain-setup would consume. But there's a **chicken-and-egg problem:**

- domain-setup needs the kernel to exist (CLAUDE.md, hooks, commands) to function
- The kernel spec would teach domain-setup how to build the kernel
- But domain-setup IS part of the kernel

**Resolution options:**
1. **domain-setup bootstraps itself** — a special first-run mode where domain-setup exists standalone and builds the rest of the kernel from the kernel spec
2. **Kernel spec is a pre-install** — the kernel spec includes a simple installer (copy files) that places the kernel, THEN domain-setup runs for domain specs
3. **domain-setup + commands are the bootstrap layer** — they always exist, and the kernel spec produces everything else (CLAUDE.md, hooks, settings.local.json)

Option 3 is most aligned with the current architecture: domain-setup and its commands are the constant primitive. The kernel spec produces CLAUDE.md, hooks, settings.local.json, and autonomous-cycling. After kernel spec install + domain-setup, you have a governed workspace ready for a domain spec.

## Gaps / Questions

1. **settings.local.json permissions** — domain-specific (npm vs pip vs docker). Should the kernel spec provide a minimal base, then domain specs extend?
2. **CLAUDE.md domain references** — cognitive-agent's CLAUDE.md has domain-specific sections. How does domain-setup merge kernel + domain sections?
3. **Hook customization** — all repos use identical hooks. Should hooks be part of the kernel spec or always the same (true constant)?
4. **Cycling skill** — is it part of the kernel or a separate "add-on" spec? It's in the canonical kernel now.
