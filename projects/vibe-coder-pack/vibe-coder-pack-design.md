 Vibe Coder Pack: Spec-Driven Development for Any Stack 

 Context

 We have two working QA domain packs (Python/Selenium and TypeScript/Playwright) that   
 prove the Isagawa Kernel can manage AI agents across tech stacks. The next product is  
 a vibe coder pack — a set of specs (markdown files) that teach the kernel how to be a  
 senior software engineer for people building apps with AI.

 Target user: Vibe coders — people who know what they want their app to DO but don't    
 know frameworks, stacks, or architecture. They describe features in plain English. The 
  agent handles all technical decisions.

 Key difference from QA packs: QA has fixed architecture (5 layers, pre-written
 references). The vibe coder pack has dynamic architecture — the agent asks discovery   
 questions, makes stack/architecture decisions with the user (HITL + education),        
 generates its own reference docs, then enforces them on itself. Same kernel, same      
 loop, different domain.

 Repo: D:\my_ai_projects\project_test_repos\vibe-coder-pack

 ---
 Architecture

 How It Works

 1. User clones the repo (contains only kernel + skill pack specs)
 2. Runs /vibe — agent asks discovery questions about their app
 3. Agent presents stack/architecture options with educational explanations (HITL)      
 4. User picks, agent generates architecture.md — THE protocol reference
 5. Agent scaffolds the project, runs domain-setup, builds protocol from generated      
 architecture
 6. User describes features in plain English via /vibe-feature
 7. Agent builds with enforcement active — every file checked against architecture.md   
 8. Failures get recorded as lessons, enforcement gets tighter

 Self-Binding Pattern

 The agent generates _generated/architecture.md during setup, then the kernel treats it 
  as the protocol reference (same as QA's _reference/ folder). The agent creates its    
 own constraints, then enforces them on itself.

 Skill Pack: vibe-coder-guidance

 Phase Flow

 Phase 1: Discovery ──► app-profile.md
     │
 Phase 2: Decisions ──► architecture.md + stack-profile.md + decisions/
     │
 Phase 3: Scaffold  ──► working project with smoke test passing
     │
 Phase 4: Feature   ──► (LOOP) user describes feature → agent builds it

 Phases 1-3 run once per project. Phase 4 repeats for every feature.

 Phase 1: Discovery (phase-01-discovery.md)

 Conversational intake — 4 questions, plain English:

 ┌─────────────────────────────────┬─────────────────┬──────────────────────────┐       
 │            Question             │     Purpose     │          Drives          │       
 ├─────────────────────────────────┼─────────────────┼──────────────────────────┤       
 │ "What does your app do?"        │ Core value prop │ Everything               │       
 ├─────────────────────────────────┼─────────────────┼──────────────────────────┤       
 │ "Who uses it?"                  │ Users, scale    │ Auth, UX complexity      │       
 ├─────────────────────────────────┼─────────────────┼──────────────────────────┤       
 │ "Web, mobile, or both?"         │ Platform        │ Frontend stack           │       
 ├─────────────────────────────────┼─────────────────┼──────────────────────────┤
 │ "Any services you already use?" │ Constraints     │ Deployment, integrations │       
 └─────────────────────────────────┴─────────────────┴──────────────────────────┘       

 Output: _generated/app-profile.md
 Gate: User approves the profile

 Phase 2: Decisions (phase-02-decisions.md)

 For each decision area (frontend, backend, database), the agent:
 1. Reads the decision tree (_decision-trees/*.md)
 2. Evaluates against app profile
 3. Presents 2-3 options with educational context (HITL)
 4. User picks, agent records decision

 Educational HITL format:
 DECISION: [Area]

 Your app needs [what this does — plain English].

 OPTION A: [Name]
   What it is: [1 sentence]
   Best for: [use case]
   Tradeoff: [honest downside]

 OPTION B: [Name]
   ...

 MY RECOMMENDATION: [Option] because [tied to THEIR app]

 Which do you prefer?

 Output: _generated/architecture.md + _generated/stack-profile.md +
 _generated/decisions/*.md
 Gate: User approves architecture.md at architecture-review checkpoint

 Phase 3: Scaffold (phase-03-scaffold.md)

 Agent generates a working project:
 1. Create file structure matching architecture.md
 2. Initialize package manager + dependencies
 3. Create config files (.env.example, etc.)
 4. Write one smoke test
 5. Verify dev server starts + test passes
 6. Generate README with setup instructions
 7. Init git

 Gate: Dev server runs, smoke test passes

 Phase 4: Feature (phase-04-feature.md) — REPEATING LOOP

 1. User describes feature in plain English
 2. Agent generates feature spec (_generated/features/[name].md)
 3. HITL pre-build checkpoint — agent presents plan, user approves
 4. Agent builds following architecture.md patterns
 5. Agent writes tests, runs them
 6. If fail → on-failure checkpoint → /kernel/learn
 7. HITL feature-complete checkpoint — user tries feature, approves

 Decision Trees

 Decision trees are markdown files with conditional logic the agent follows. Each tree: 
 - Starts with a question about the app
 - Branches based on answers
 - Leads to 2-3 recommendations with tradeoffs
 - Includes "Explain to User" sections in plain English

 MVP Decision Trees (3)

 frontend-stack.md — Web? Mobile? Both? → React/Next.js, React Native, Vue, etc.        
 backend-stack.md — Needs API? Real-time? → Node/Express, FastAPI, Supabase, etc.       
 database-stack.md — What data? Scale? → Postgres, MongoDB, SQLite, Supabase, etc.      

 Deferred Decision Trees

 - auth-strategy.md (OAuth, JWT, Supabase Auth, etc.)
 - deployment-stack.md (Vercel, Railway, Fly.io, etc.)
