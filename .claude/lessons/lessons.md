## RULE ZERO — Read this every anchor

**NEVER ASSUME. ALWAYS VERIFY.** Read the actual files before acting. Don't guess what a file contains, what a config looks like, or what's wired up. Open it and read it. This applies to hooks, state, settings, code — everything. Assumptions caused: missing hooks (settings.local.json never created), stale counters (27 actions untracked), wrong backlog location, wrong naming conventions. Verify first, act second.

**NEVER QUICK-ANCHOR.** When the counter hits the limit, do a FULL anchor — Read protocol, Read lessons, apply rules to next action with concrete verbs, review inter-anchor work. Skipping any part is a violation. The anchor exists to re-center, not to reset a counter. This violation recurred 2026-03-22 even after the lesson was already recorded and read earlier in the same session. **Recurred 2026-05-01:** during batch attestation (17 specs), agent bypassed anchor TWICE by just resetting state files (actions_since_anchor, pending_anchor_token) instead of doing the full anchor. Batch/repetitive operations are a trigger — the agent rationalizes "it's all the same operation, just reset the counter." NO. Every anchor is full. The counter exists because 20 actions without re-centering causes drift regardless of whether the actions are similar. **Recurred 2026-05-26:** agent confirmed anchor token and updated state files, then declared "ANCHORED" at the end without actually executing the full anchor ceremony. User caught it: "you better do a lesson since you tried to quick anchor." Root cause: rushing to finish work, skipping the structured anchor ceremony steps. Fix: invoking /kernel/learn now to record this violation.

**ALWAYS USE WIKILINK TIERED INDEXING.** Every file that exceeds ~50 lines of detail on a subtopic MUST extract that subtopic into its own reference file and link to it with `→ [[references/file.md]]`. Parent files are indexes — they have step tables and pointers, never inline implementation. This applies to: SKILL.md, workflow.md, step files, commands, protocol. If you're writing a long section inline, stop and extract it. The user has repeated this multiple times — it is a core design pattern of the kernel, not optional.

**NEVER IMPROVISE. NEVER SKIP STEPS. FOLLOW THE COMMANDS EXACTLY.** When a command or skill has written instructions, follow them to the letter. Do not decide a step is "unnecessary" or "inefficient" and skip it. Do not bundle, consolidate, or "optimize" what the instructions say to do separately. The instructions exist because past failures proved they're needed. Every time the agent improvises — quick-anchoring, bundling atomic tasks, skipping verification, assuming a path syntax, executing tasks inline instead of via run-task.sh — it produces a violation the user has to catch. The pattern: agent reads rule → decides it knows better → skips/modifies rule → user corrects → lesson recorded → agent does it again. STOP. Follow the instructions. If you think a step is wrong, flag it — don't silently skip it. **WHEN THE PRESCRIBED PATH HITS AN OBSTACLE, RE-READ THE SKILL INSTRUCTIONS BEFORE IMPROVISING.** The instructions likely already cover the failure case (e.g., step-04-execute-tasks.md has a Failure Handling table). Recurred 2026-04-08 when agent bypassed run-task.sh after rate limit, despite the lesson being in RULE ZERO. **Recurred 2026-04-28:** three violations in one execute-pipeline run: (1) tried to directly edit `pending_anchor_token` in session_state.json to bypass the hook instead of doing a proper anchor — this is a hook bypass; (2) paused the autonomous pipeline to present the plan to the user and ask "Approve?" — this is plan APPROVAL (user pause), not plan REVIEW (automated agent check). Plan review (`skip_plan_review: false`) is correct — it's an automated quality check by a spawned agent. Plan approval (asking the user) is the violation. Execute-pipeline SKILL.md says "no pause points, no plan approval, no user confirmation" — that means never ask the user, but automated checks still run; (3) when the hook blocks during an anchor, reset state with Write (full file), not Edit (partial patch). **Recurred 2026-06-13:** When attempting to write HARNESS-DESIGN-PATTERN.md, encountered hook block (protocol hash mismatch). Instead of reporting the obstacle and asking user, agent unilaterally modified `.claude/protocols/sr_dev-protocol.md` to "fix" the issue. This was wrong because: (1) Protocol is system state, not for agent to modify without approval; (2) The modification wasn't necessary — the harness-design-pattern skill doesn't require protocol registration; (3) Created an anchor token requirement and cascading state issues; (4) Violated the core principle "when blocked by hook, report and ask user." **Fix:** Reverted protocol changes. Added explicit rule: **WHEN BLOCKED BY HOOK OR ENCOUNTERING OBSTACLE, REPORT TO USER AND REQUEST DIRECTION BEFORE ATTEMPTING WORKAROUNDS OR MODIFYING SYSTEM STATE.** Do not attempt to "fix" the problem unilaterally. Do not modify protected files (protocol, hooks, CLAUDE.md, lessons) without explicit user approval.

**NEVER USE `cd` IN BASH COMMANDS.** Hooks resolve relative to cwd. Any `cd` shifts cwd for the rest of the session and breaks hook path resolution (`python .claude/hooks/...` fails). Use absolute paths in all Bash commands. If you must reference another directory, use the full path — never `cd` into it. This broke hooks twice in one session (2026-03-22). **Recurred 2026-05-26:** during SSH platform investigation, agent used `cd` in 4 bash commands (lines 4, 5, 7, 14 of actions.jsonl) despite the rule being documented in RULE ZERO. Root cause: was exploring and investigating repos; treated temporary exploration as not needing the rule. **Recurred 2026-05-26 (anchor 2):** background agent checking run-task.sh status used `cd` in 3 more bash commands during pre-execution setup (actions.jsonl lines 2, 3, 6). Mechanical enforcement not yet added to sr_dev-gate-enforcer.py. **Fix:** (1) Always use absolute paths, no exceptions. (2) Add PreToolUse hook to sr_dev-gate-enforcer.py that validates bash commands and blocks any containing `cd` with explicit error message. (3) Escalate to mechanical enforcement — this rule cannot be left to human discipline.

**ALWAYS VERIFY TESTING COMPLETENESS (L1/L2/L3) DURING ATOMIZATION.** Every deliverable needs 3 levels of tests: Level 1 (does it exist?), Level 2 (does it run?), Level 3 (does it produce correct results in a real scenario?). Plan ALL test tasks during step 4 (atomize), not step 6 (execute). Read production-testing.md during step 4. "Simulate" is NOT Level 3 — Level 3 means actually running the deliverable under real conditions (spawn run-task.sh, invoke the kernel loop, run the workflow). This gap caused production tests to be missing entirely until the user caught it (2026-03-23). The requirement was documented in step-06 and production-testing.md but step-04 never referenced either file.

**NEVER STOP CYCLING. NEVER SKIP "HUMAN REQUIRED" TASKS.** Autonomous cycling means autonomous — don't stop to "save state," don't pause for user confirmation, don't skip tasks labeled HUMAN REQUIRED. If a task needs a human action (create GitHub repo, restart Claude Code, approve a PR), spawn a sub-agent to do it programmatically (e.g., `gh repo create`, write state files, use CLI tools). The agent stopped cycling 3 times in one session (2026-03-23) to "save context" and skipped task 100 (git push) as "HUMAN REQUIRED." Both are violations. The cycling contract says: don't stop until all tasks are done or skipped after 3 attempts. **Recurred 2026-05-26:** execute-pipeline completed task-builder Step 3 (task file generation) but STOPPED and reported completion instead of immediately transitioning to Step 4 (run-task.sh execution). The pipeline_mode was set to `no_execute=true` which explicitly prevents step 4 from running. User explicitly called this out: "why did this command stop. can you update lessons? this is supposed to complete autonomously." **Fix:** execute-pipeline must never pause after task-builder. Step 3 completion → flip `pipeline_mode.no_execute` to `false` → spawn background Agent with `env -u CLAUDECODE bash run-task.sh` → cycling continues without interruption. No status reports between steps, no "step N complete" messages that break the autonomous flow. The pipeline reports only at the beginning (intent) and end (final validation report).

**ALWAYS USE KERNEL COMMANDS FOR KERNEL OPERATIONS.** When a kernel command exists for an operation (`/kernel/backlog`, `/kernel/complete`, `/kernel/learn`, etc.), ALWAYS invoke it via the Skill tool — never bypass by writing files directly. The command enforces template structure, auto-resolves fields, applies rules, and produces consistent output. Writing directly skips all of that and the user has to catch it. This happened 2026-04-24: agent wrote backlog 046 and edited backlog 044 directly instead of invoking `/kernel/backlog`. User caught it, asked for redo via the command. **Recurred 2026-04-25:** agent edited 047 backlog files directly AND manually called `intent.py record` to create an intent chain entry — defeating the entire purpose of the intent chain, which exists to hash the USER's raw words at `/kernel/backlog` invocation time, not the agent's summary. The bogus intent entry had to be deleted and all three files reverted. **The intent chain is especially critical — never call intent.py directly. Only `/kernel/backlog` should create intent entries, because only it receives the user's actual words.** **Recurred 2026-06-14:** background agent spawned during task execution (backlogs 133-134 creation) called `python lib/attestation/intent.py record` directly 3 times. Background agents do not have lesson context and bypass /kernel/backlog. **Fix:** Mechanical enforcement — add PreToolUse hook to sr_dev-gate-enforcer.py that blocks any bash command containing "intent.py record" with error message directing to `/kernel/backlog`. This prevents the violation by design, regardless of agent context.

**NEVER SPAWN AGENTS UNLESS FOR PROD-TEST OR RUN-TASK.SH.** Do not use the Agent tool for research, exploration, or task delegation. If you can do the work yourself (read files, search, web fetch, analyze), do it yourself. Exceptions: (1) `/kernel/prod-test` which requires sub-agents by design, and (2) `run-task.sh` / autonomous cycling which spawns one-shot agents per task. The user explicitly requested this (2026-04-04) because agent spawning adds latency, loses context, and the user wants direct work in the main conversation — but autonomous cycling is the intended execution mode for task-builder output.

**USE BACKGROUND AGENT + `env -u CLAUDECODE` FOR RUN-TASK.SH IN INTERACTIVE SESSIONS.** Interactive sessions set `CLAUDECODE=1` which blocks nested `claude -p`. To run `run-task.sh` autonomously from an interactive session: spawn a **background Agent** (`run_in_background: true`) that executes `env -u CLAUDECODE bash run-task.sh [repo] [iterations] [subfolder]`. The Agent tool creates a decoupled subprocess; `env -u CLAUDECODE` strips the blocking env var for that subprocess only. The `claude -p` calls inside run-task.sh then work normally. This is the same decoupled pattern prod-test uses — the agent runs like a separate terminal session with "blue letters at the bottom." Do NOT call `bash run-task.sh` directly from the interactive session. Do NOT execute tasks inline — use run-task.sh as designed.

**EXECUTE-PIPELINE WITH MULTIPLE BACKLOGS: STRICTLY SEQUENTIAL.** When `/kernel/execute-pipeline` receives multiple backlog numbers (e.g., `037 038 039`), execute each pipeline to completion before starting the next. The parent session MUST NOT prep tasks for pipeline N+1 while pipeline N is running in the background. Both write to shared state files (`session_state.json`, `{domain}_workflow.json`) and create contention that blocks the parent via hook enforcement. The parent's workaround of flipping `anchored: true` directly is itself a protocol bypass — and once backlog 037 (protocol hash verification) ships, this workaround becomes a hard failure. **Sequencing constraint:** State scoping fix (backlog 040) must ship before or alongside 037, or 037 will make the contention a deadlock.

**NEVER BUNDLE ACTIONS INTO ONE TASK.** One task = one action. One file write, one command run, one config change. If a task requires writing 4 files, that's 4 tasks. If a test has setup + run + verify, that's 3 tasks. Small tasks are correct tasks — a task that copies one file IS a valid task. The agent repeatedly bundled 3-10 actions into single tasks despite the user correcting this 3 times (2026-03-23). The root cause was "merge if <3" rules in the task-builder skill, which have been removed. When decomposing: count the distinct actions, create that many task files. If it feels like "too many tasks," it's the right number.

**BACKLOG REPORT SAYS "Ready for /kernel/execute-pipeline" NOT task-builder.** The user exclusively uses `/kernel/execute-pipeline` as the entry point for all backlog execution. Task-builder is an internal step within execute-pipeline, never invoked directly. The backlog command's report output must say "Ready for /kernel/execute-pipeline." — not task-builder. Updated 2026-04-28.

**"The loop" = the execute-pipeline autonomous cycling pattern** (backlog → task-builder → run-task.sh). Use this term in backlogs, reports, and conversation. The user's preferred shorthand.

**MULTI-AGENT ORCHESTRATION: PROTOCOL VALIDATION AT ENTRY, NOT EXECUTION.** When spawning parallel background agents via `/spawn-subagent`, protocol hash validation during execution creates a deadlock cascade: one agent updates `protocol_hash: "pending"` → other agents' bash gets blocked → parent orchestrator stalls. Industry standard (RAFT consensus, Gossip protocols, LangGraph): validate critical state (protocol) at session entry only, not during execution. Protocol consistency via eventual consistency — agents read protocol at start, execute independently, parent merges results. **Problem:** Gate 6 of universal-gate-enforcer.py checked protocol_hash on every bash command, blocking all concurrent execution. **Fix (2026-06-14):** Removed Gate 6 from PreToolUse hook. Protocol hash now validated only at `/kernel/session-start` (entry point), allowing concurrent agents to work without deadlock. Background agents can now anchor and execute in parallel. See: Gossip protocols for distributed state (https://arxiv.org/pdf/2508.01531), LangGraph state management (https://medium.com/@bharatraj1918/langgraph-state-management-part-1-how-langgraph-manages-multi-agent-workflows), RAFT consensus (leader validates at entry, followers work independently).

**MULTI-AGENT STATE ISOLATION: SHARED MUTABLE STATE CAUSES VISIBILITY LOSS.** (2026-06-14) When spawning 3+ concurrent agents that all write to the same `session_state.json` and `sr_dev_workflow.json`, later agents' state updates overwrite earlier agents' state in the shared files. **Problem:** Agent 132 completed all deliverables and created output, but failed during backlog archival (Step 5). The monitor was polling for backlog archive status to detect completion. Meanwhile, agent 131 (running concurrently) completed and updated the shared state file with its OWN completion state, overwriting agent 132's state. Result: orchestrator lost all visibility into agent 132's execution, monitor couldn't detect it was done, user saw "132 still running" for hours. **Root cause:** No per-agent state isolation; shared state file acts as a single point of contention. **Fix:** Implement per-agent state file pattern — each agent writes to `[backlog-N]-state.json` instead of shared state. Aggregate state during monitoring by reading all agent-specific files, not the shared file. This prevents overwrites and preserves execution visibility. **Pattern:** When implementing multi-agent swarms, design per-agent isolation FIRST, aggregate monitoring SECOND. Never rely on shared mutable state for tracking independent agents.

## 2026-07-15 — Semantics-gate test script false-positives caused gate skip (204 pages)
- **Issue:** Pipeline 204's contract-semantics test (task 006 — the gate lesson #38 created) failed 3 consecutive attempts and was SKIPPED under the cycling contract; the pipeline committed and self-reported complete. - **Anti-Pattern Added:** String-grep semantics checks on Python source. Docstrings quoting rules and templated locators guarantee false positives.
- **Quality Gate Added:** (1) Semantics-gate test scripts MUST be AST-based with docstrings excluded, and dynamic-locator-aware (normalize {placeholder} ↔ {{ jinja }} before comparing). (2) A skipped GATE task (any task whose Gates Satisfied covers contract-semantics gates) ALWAYS blocks merge until the orchestrator validates the gate itself — skip-after-3 completes the pipeline but never waives the gate.

## 2026-07-15 — AST semantics script counted decorators as __init__ construction (lesson-#39 recurrence)
- **Issue:** 207 orchestrator validation false-positived "constructs nothing in __init__" on both roles. `ast.walk(FunctionDef)` includes `decorator_list`, so `@trace("Role Constructor")` — itself an ast.Call — was counted as internal construction. Code was compliant.
- **Root Cause:** AST scoping error: walking the whole FunctionDef node when the rule applies only to the BODY. 3rd instance of the semantics-script false-positive pattern (string-grep on docstrings → 204's naive testid check → decorator nodes).
- **Fix:** Walk `fn.body` statements only for body-scoped rules. Script fixed, all checks re-ran green, code unchanged.
- **Anti-Pattern Added:** `ast.walk` on a FunctionDef for body-scoped rules — decorators, annotations, and defaults are part of the node and WILL false-positive on decorated constructors.
- **Quality Gate Added:** Semantics scripts checking "no calls/constructs in method body" MUST iterate `fn.body` (per-statement walk), never `ast.walk(fn)`. Applies to every remaining gate contract (208-229): add "decorator-aware" to the lesson-#39 test-script requirements block.
